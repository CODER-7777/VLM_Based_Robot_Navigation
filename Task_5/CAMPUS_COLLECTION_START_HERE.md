## 1. Generate your private certificates on the laptop

Open a laptop terminal:

```sh
cd /home/vivekananda/UGP_1_VLM/VLM_Based_Robot_Navigation/Task_5
python3 -B campus_collector/create_private_certificates.py
```

OpenSSL asks for a password for the new CA private key, confirmation, then the same password to sign the server certificate. Choose a strong password of at least 12 characters and keep it private. The helper checks that the generated certificate verifies for `172.26.186.222`. It prints the public CA SHA-256 fingerprint for verification by contributors.

The helper requires OpenSSL 3, makes owner-only folders, and refuses to overwrite an existing `certificates/` directory. It does not install a trusted root or change networking. If it stops with partial files, review those files before retrying; do not erase a CA that contributors already trust. Issued server certificates last 365 days and require renewal before expiry. Ordinary website updates do not require generating certificates again.

Keep these values:

The example already contains the other required settings. The absolute `data_root` keeps server accounts and recordings in your requested `data_collecting/data/` directory regardless of the terminal's working directory. Relative certificate paths are resolved against the configuration's folder. If you already created `config.production.json` before this storage change, edit its `data_root` as shown; `cp -n` preserves an existing configuration.

**Fill `allowed_networks` with the actual campus client CIDRs confirmed by your lab/network administrator.** The default empty list intentionally prevents startup. A laptop IP or Wi-Fi SSID does not establish all campus ranges. Do not use all private addresses or `0.0.0.0/0`. Decide explicitly whether IITK VPN client ranges are included.

Ask the administrator to allow approved campus clients to server port 8443 and deny other sources at the host/campus firewall. Do not expose worker ports 9100–9101 or existing collector ports 8876/8878. The gateway independently enforces its allowlist, but it cannot open a firewall or discover IITK policy. The existing [IT request](campus_collector/IT_REQUEST.md) lists the details needed. For the private-CA route, a new hostname/publicly trusted certificate is optional; confirmed client networks and reachability are still necessary.

Choose a separate study password of at least 12 characters for each contributor and enter it again to confirm. Create each account once; they reuse it for future recordings. Existing accounts continue to work. The website provides sign-in only, with no registration or invitation code.

Contributors do not receive SSH credentials and should not reuse an IITK CC password. Account creation is limited to your server terminal.

If a contributor forgets their password, verify their identity through your study channel, let active recordings/uploads finish, then use the owner-only server command:

```sh
python3 -B gateway.py --config config.production.json --reset-password contributor_id
```

It asks for and confirms a replacement password, revokes old sign-in sessions, and preserves recordings. There is no email verification, automated email reset or IITK SSO integration in this version.

## 5. Start the server website

After the allowlist and firewall are ready, in the same server directory:

```sh
sh start_campus_collector.sh config.production.json
```

The launcher uses tmux when available, or the systemd user service manager otherwise. This server currently uses systemd because tmux is not installed. Check its status/logs with:

```sh
systemctl --user status data-from-dashboard-collector.service
journalctl --user -u data-from-dashboard-collector.service -f
```

Press Ctrl-C to stop following logs; this does not stop the service. If the launcher uses tmux on another server, attach with `tmux attach -t task5-campus-collector` and detach with Ctrl-b, then d. Rerunning the launcher reuses a running service/session; it does not automatically deploy or reload code changes.

## 6. Install trust on each contributor device once

Give each contributor **only** `Task_5/campus_collector/certificates/share/rootCA.crt`. They must explicitly trust your private CA on the device/browser used for the study. Its installation can require administrator permission. This trust allows certificates issued by your CA, so they should verify its fingerprint with you first.

For an Ubuntu contributor who has placed the file under their own `Task_5/campus_collector/certificates/share/`, run these commands from their Task_5 folder:

```sh
openssl x509 -in campus_collector/certificates/share/rootCA.crt -noout -fingerprint -sha256
sudo install -m 0644 campus_collector/certificates/share/rootCA.crt /usr/local/share/ca-certificates/task5-collector-root.crt
sudo update-ca-certificates
```

The `/usr/local/share/ca-certificates/` copy registers the public certificate with the operating system; the original project file stays in Task_5. Restart the browser. Some browser installations have a separate certificate store; import the same public root as a trusted website certificate authority if the browser still does not trust it. Windows/macOS devices need the equivalent trusted-root installation using their certificate settings. Other setup files stay in the laptop's Task_5 or the server's Data_from_Dashboard directory. The issuing CA private key stays on your laptop.

## 7. Verify access before sharing widely

- From an approved IITK device: sign in, record a short sample and check its server files.
- With two contributor accounts: check independent navigation and separate saved files.
- From an outside connection: access must be denied or unreachable even with the public root certificate installed. VPN behavior must match the agreed policy. This outside-device check must actually be performed; localhost tests cannot prove campus firewall boundaries.

The private CA enables HTTPS trust. The network allowlist/firewall enforces IITK-only reachability. Contributor accounts identify recordings. All three controls remain necessary for this workflow.

## Website updates keep the same link

Request the change, deploy the updated application to the server, and refresh the contributor browser after the update is ready. Local edits alone do not change the running server. Active recording sessions must finish and uploads must be saved before restarting affected workers/gateway. Worker application templates are copied when a contributor's worker starts, so existing workers may retain an earlier version until safely restarted. Normal updates do not replace the certificate or the URL. Keep the same CA so existing contributor trust stays valid; handle expiry separately.

The archive from step 2 is for initial setup. Do not repeatedly extract it over running workers as an update mechanism. Future deployments should copy changed application files while preserving the recording root in `data_collecting/data/`, `certificates/` and `config.production.json`.
